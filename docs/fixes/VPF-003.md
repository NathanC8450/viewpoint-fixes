# VPF-003: inventory "Place item" (free 3D placement)

- **Status:** fixed (ours), verified in game with a radio in crosshair and cursor mode, and with a controller
- **Seen on:** Viewpoint 0.1.5a-hotfix, Project Zomboid 42.21
- **Code:** `.../ViewpointFixes/fixes/VPF_003_PlaceItemCursor.lua` (uses `Adapter.lua`); Java: `java/src/main/java/viewpointfixes/` (`Patch_VPF_003_PreviewItem`, `Preview`, `Aim`, `Keys`, `Bridge`)

## Symptom
Inventory, right-click an item, Place Item: in 2D the item follows the mouse, R and Shift+R rotate it in 5 degree steps, Tab cycles surface heights, and a click places it. With Viewpoint's view on, the mode starts but the item doesn't follow the aim, can't be rotated, can't be placed, and no preview shows.

## Cause
1. The cursor does almost all its work in `renderOpaqueObjectsInWorld`, which only runs from the iso world render's event. Viewpoint replaces that render, so there is no position, rotation, surface or preview.
2. Viewpoint hides keys from the game (its patch on `KeyboardState.isKeyDown`), so R never reads as held.
3. Viewpoint's loot menu takes R, Tab and F in crosshair mode.
4. Viewpoint's Lua mouse point (`Mouse.worldX/Y`) is nil in crosshair mode, and nil while the pointer is moving in cursor mode. The crosshair pick and the latest cursor pick exist only in Java.
5. The preview is drawn through the hidden iso renderer. Viewpoint draws world items only from its per-frame item list.
6. On a controller, the game places with A through a flag that the iso render sets, so A does nothing.

## What the fix does
- Every frame, runs the cursor's own `renderOpaqueObjectsInWorld` with the screen-to-world conversion answering Viewpoint's aim point, the held-button flag cleared, and the iso preview draw skipped. The game still handles surface, offsets and range.
- R and Shift+R go through the game's own rotation code, with the raw keyboard state added (read from Java).
- The preview is a throwaway copy of the item, added to Viewpoint's per-frame world-item list by a Java patch, never to a square, so it can't be saved, looted or synced.
- Viewpoint's loot menu is paused while placing and restored to the player's own setting afterwards.
- F (Viewpoint's take key) places; Shift+F places all (vanilla). On a controller, A places, and RB/LB rotate through the game's own code.
- The aim keeps its last point for 300 ms so a late pick doesn't make the preview flicker.

## If Viewpoint handled this itself
Call the cursor's per-frame logic from Viewpoint's own loop with its aim point, let the preview item join its world-item list, and either avoid the key hiding for the rotate binding or pause the loot menu for placement cursors. Our whole Java part and most `Adapter` calls would disappear.

## Check list
1. Crosshair mode: Place Item on a radio; the preview follows the crosshair; R and Shift+R rotate; F places with the rotation kept (also on a table).
2. Cursor mode: the same, with the preview following the pointer without disappearing while it moves.
3. Controller: the preview follows the camera aim; RB/LB rotate; A places.
4. Non-radio items (weapon, clothing, a stack, a large item): confirm they preview and rotate. Not yet verified.
5. After placing or cancelling, the loot menu works again.

## Retire when
Viewpoint fires the render event for placement cursors, or replaces the cursor logic. The fix already stands down when the event is arriving.
